# План реализации модуля мероприятий

## Назначение
- Модуль мероприятий реализует организационный цикл события из `WORK.md`: создание мероприятия, прием участников, обработку заявок, формирование выборки, формирование команд, построение сетки матчей, фиксацию результатов и завершение события.
- Модуль не является публичным REST API. Внешний REST находится в Gateway, а этот сервис должен предоставлять внутренние RPC-команды через RabbitMQ/FastStream.
- Модуль владеет только данными мероприятий. Пользователи, пользовательские пространства, интеграции, игровые роли, рейтинги и вычислительное ядро балансировки являются внешними модулями и должны вызываться через RPC/задачи, а не через прямой доступ к их БД.

## Требования Из WORK.md
- Поддержать разные типы мероприятий: турнирная сетка и одиночный матч.
- Поддержать мероприятия внутри пользовательского пространства, чтобы разные сообщества имели собственную базу игроков, дисциплины, роли и рейтинговые шкалы.
- Поддержать регистрацию через заявки и свободное присоединение без предварительного рассмотрения.
- Дать организатору возможность задавать обязательные игровые/социальные интеграции, дополнительные текстовые поля заявки и доступные игровые роли.
- При подаче заявки сохранить ответы на кастомные поля, выбранные интеграции и приоритеты игровых ролей участника.
- Дать организатору возможность принимать и отклонять заявки; принятая заявка должна создавать игрока мероприятия.
- Поддержать выборку игроков для конкретного цикла формирования команд, включая повторные выборки при `allow_multiple_drafts`.
- Поддержать автоматическое формирование команд с учетом рейтингов, ролей, предпочтений, размера команды и ограничений состава.
- Перед формированием команд получать эффективный рейтинг из внешнего рейтингового сервиса; в балансировщики нельзя передавать сырую `custom`/экспертную оценку.
- Для формирования команд возвращать несколько вариантов распределения с метриками качества, чтобы организатор мог выбрать один вариант.
- Поддержать капитанский драфт: назначение капитанов и выбор игроков капитанами из выборки.
- Поддержать турнирные структуры: сетка, стадии, группы, форматы стадий `single_elimination`, `double_elimination`, `round_robin`, `swiss`.
- Поддержать одиночный матч как частный случай сетки: одна стадия, одна группа, один матч.
- Фиксировать участников матча, счет команд, победителя/ничью, продвижение по сетке и итоговые места.
- После завершения мероприятия сформировать данные для модуля рейтингов, но расчет рейтинга выполняется во внешнем рейтинговом сервисе.

## Текущее Состояние
- ORM-модели и репозитории в основном отражают таблицы модуля мероприятий, но миграции не полностью синхронизированы с моделями, например в миграции нет `event_table.status`.
- Текущие `src/core/service/*.py` написаны под старую модель без DTO и неактуальны: они импортируют `src.domain.*`, используют DTO как изменяемые ORM-объекты и вызывают методы, которых нет в DTO.
- Тестовый слой также старый: `tests/conftest.py` импортирует модели пользовательских пространств из текущего сервиса мероприятий.
- Рабочей точки входа нет: `start.py` и `entrypoint.sh` ссылаются на отсутствующие модули.
- Вывод: старые сервисы нужно не чинить точечно, а заменить новым слоем use cases под текущую DTO/repository-архитектуру.

## Целевая Архитектура Модуля
- `src/core/models`: предметные DTO и enum-ы предметной области.
- `src/core/commands`: входные DTO команд RPC, например `CreateEventCommand`, `SubmitApplicationCommand`, `GenerateBracketCommand`.
- `src/core/results`: DTO результатов сложных операций, например `TeamFormationVariant`, `BracketView`, `EventSummary`.
- `src/core/interfaces/repo`: протоколы репозиториев, уже частично есть.
- `src/core/interfaces/clients`: протоколы внешних сервисов: `SpaceClient`, `IdentityClient`, `RatingClient`, `BalancerClient`.
- `src/core/usecases`: новый слой сценариев вместо текущих stale services.
- `src/infra/postgre/models` и `src/infra/postgre/repo`: ORM и репозитории PostgreSQL.
- `src/infra/rabbit`: FastStream app, RPC handlers и publishers задач.
- `src/infra/clients`: RabbitMQ RPC-клиенты внешних сервисов.
- `src/config/event_flow.ini`: источник допустимых переходов статусов события.

## Интеграция С Внешними Сервисами
- Подробный контракт зафиксирован в `EXTERNAL_BALANCER_RANKER_INTEGRATION.md`; при расхождении использовать код внешних сервисов как источник истины.
- Контракт с Gateway/Server Service зафиксирован в `SERVER_GATEWAY_EVENT_INTEGRATION.md`; Event Service получает `access_data` от Gateway и не вычисляет permission/restriction masks самостоятельно.
- Рейтинг-сервис `mixtura_ranker` предоставляет RPC `rating.effective.calculate` и `rating.match.process`.
- Перед балансировкой модуль мероприятий должен отправить в `rating.effective.calculate` открытые оценки игроков по ролям и получить `effective_rating` для каждой пары `member_id + role_id`.
- В `mixtura_balance` и `mixtura_balancer_tournament` поле `PlayerRole.rating` должно заполняться эффективным рейтингом из ranker, а не сырой оценкой организатора.
- `mixtura_balance` слушает `mix_balance_service.balance` и подходит для одиночного матча/двух команд.
- `mixtura_balancer_tournament` в текущем `app/main.py` слушает `tournament_balance_service.balance` и публикует прогресс в `mix_balance_service.balance.progress`; README/examples в том репозитории местами используют старое имя `mix_balance_service.balance`, это нужно выровнять до интеграции.
- После фиксации результата матча модуль мероприятий должен отправлять `rating.match.process` с командами, рангами и снимком open-rating игроков на момент матча.
- Server Service уже содержит restrictions `server_ban`, `mix_ban`, `tournament_ban`; Event Service должен применять их при создании/участии в мероприятиях.
- Server Service пока не содержит event-specific permissions. Для MVP не перегружать чужие permissions: использовать локальных organizers в Event Service плюс проверку членства/restrictions, либо отдельно добавить event-specific permissions в Server Service.

## Исправление Модели Данных
- Добавить к `Event` поле `server_id`, иначе модуль не выполняет требование изоляции мероприятий по пользовательским пространствам.
- Явно оформить enum-ы: `EventMatchType`, `RegistrationType`, `TeamFormation`, `EventStatus`, `ApplicationStatus`, `DraftStatus`, `StageFormat`, `MatchSlotSourceType`, `BracketPosition`.
- Не вводить отдельные create/read DTO без необходимости. Для доменных сущностей допустима единая DTO-модель, если поля вроде `id`, `status` и timestamps имеют серверные дефолты или могут быть `None` до сохранения.
- Отдельные command DTO нужны на RPC-границе, когда входной запрос отличается от доменной сущности: например `CreateEventCommand`, `SubmitApplicationCommand`, `RecordMatchResultCommand`.
- Не мутировать frozen DTO. Обновления выполнять через отдельные `Update` DTO, `model_copy(update=...)` или репозиторные patch-методы.
- Перенести статусные переходы из несуществующих методов DTO в use cases или доменные функции: `open_registration`, `start_formation`, `start_event`, `complete_event`, `cancel_event`.
- Уточнить `Draft`: в терминах работы это выборка игроков, а не только драфт капитанов. Название в коде можно сохранить, но в use cases использовать термин `selection`/`draft` как выборку.
- Добавить модель результата формирования команд, если варианты должны храниться до выбора организатором: `team_formation_job`, `team_formation_variant`, `team_formation_variant_player`.
- Добавить статусы/поля для игрока мероприятия, если нужно различать активных, ожидающих, выбранных в текущую выборку и уже играющих.
- Синхронизировать Alembic с текущими ORM-моделями и новыми таблицами.

## Этап 1. Стабилизация Базы
- Заменить старые импорты `src.domain.*` на `src.core.*` или удалить старый сервисный слой перед переписыванием.
- Привести `src/core/models` к единому контракту DTO: одна доменная DTO на сущность, без обязательных клиентских значений для серверных полей при создании.
- Починить `BaseRepository`: создание должно принимать доменную DTO/данные без заранее заданного `id`, чтение должно возвращать эту же доменную DTO.
- Синхронизировать `src/infra/postgre/models`, DTO и Alembic.
- Обновить `tests/conftest.py` под текущий модуль мероприятий или временно заменить на минимальные фикстуры PostgreSQL для event-моделей.
- Критерий готовности этапа: `uv run mypy src` проходит, `uv run pytest --collect-only` проходит.

## Этап 2. Внешние Контракты Модуля
- Описать RPC-команды Gateway -> Event Service для синхронных операций: создание/чтение/обновление события, настройки регистрации, подача заявки, обработка заявок, получение списков, фиксация результата матча.
- Описать RPC-запрос Event Service -> Rating Service: `rating.effective.calculate` перед каждым запросом формирования команд.
- Описать RPC/очереди Event Service -> Balancer Services: `mix_balance_service.balance` для двух команд и `tournament_balance_service.balance` для турнирного формирования нескольких команд.
- Описать RPC-запрос Event Service -> Rating Service: `rating.match.process` после фиксации результата матча.
- Описать RPC-зависимости Event Service -> Server Service по `SERVER_GATEWAY_EVENT_INTEGRATION.md`: `member.by_user`, `server.get_info`, `member.get`, `member.list`, `role_set.get_by_server`, `rating_set.get_by_server`, `custom.get_by_member`.
- Зафиксировать MVP-модель доступа: локальные organizers в Event Service плюс `access_data.member_id`, `server_ban`, `mix_ban`, `tournament_ban`; event-specific permissions добавить в Server Service только после отдельного решения.
- Реализовать FastStream app, dependency wiring и healthcheck.
- Критерий готовности этапа: сервис стартует локально, RPC handlers импортируются, отсутствуют ссылки на старые `src.domain` и `src.infra.static`.

- Реализовать `CreateDraftUseCase` как формирование выборки: выбрать игроков мероприятия вручную или автоматически по лимиту, статусам, pinned-флагу и ограничениям.
- Реализовать назначение капитанов для captain draft.
- Реализовать подготовку рейтингового снапшота: собрать open-rating по ролям, вызвать `rating.effective.calculate`, сопоставить ответ обратно с игроками и ролями.
- Реализовать постановку задачи формирования команд во внешний балансировщик: подготовить игроков, роли, эффективные рейтинги, предпочтения, subroles и ограничения.
- Выбирать `mixtura_balance` для двухкомандного одиночного матча и `mixtura_balancer_tournament` для турнирного формирования нескольких команд.
- Сохранять несколько вариантов распределения с метриками: разница силы команд, ролевое соответствие, разброс рейтингов, нарушения ограничений.
- Сохранять не только итоговые команды, но и rating snapshot: open-rating, effective-rating и источник/время расчета для диагностики решений.
- Реализовать выбор варианта организатором и материализацию в `Team`/`TeamPlayer`.
- Реализовать captain draft flow: капитаны выбирают игроков из выборки, после завершения создаются команды.
- Критерий готовности этапа: из утвержденных игроков можно получить несколько вариантов команд и зафиксировать выбранный вариант.

## Этап 6. Сетки, Стадии И Матчи
- Реализовать создание `Bracket` для события.
- Реализовать создание стадий и групп с настройками формата: single elimination, double elimination, round robin, swiss.
- Реализовать одиночный матч как генерацию bracket -> stage -> group -> match -> slots.
- Реализовать seed участников в `BracketPlacement` с учетом рейтингов команд.
- Реализовать генераторы матчей по форматам:
- `single_elimination`: дерево победителей, BYE для неполной степени двойки.
- `double_elimination`: верхняя и нижняя сетки, маршрут победителей/проигравших.
- `round_robin`: все пары внутри группы, `meetings_per_pair`.
- `swiss`: генерация следующего раунда по текущим очкам без повторных пар.
- Критерий готовности этапа: для каждого формата создается валидный набор `Match`, `MatchSlot`, `MatchScore` stubs.

## Этап 9. MVP-Срез

- MVP-2: выборка игроков, расчет эффективных рейтингов через ranker и автоматическое формирование команд через существующий внешний балансировщик.
- MVP-3: одиночный матч и single elimination bracket.
- MVP-4: фиксация результатов, продвижение по сетке, завершение события.

- После MVP: double elimination, swiss, round robin groups, выравнивание очередей tournament balancer, расширенные метрики и повторные draft-циклы.

## Не Делать На Первом Этапе
- Не восстанавливать старые `src/core/service/*.py` точечными правками: они концептуально расходятся с текущей DTO-моделью.
- Не добавлять unsuffixed ORM aliases в `src.infra.postgre.models` ради старых импортов.
- Не реализовывать публичный REST внутри этого сервиса; REST принадлежит Gateway.
- Не обращаться напрямую к БД auth/space/rating сервисов; только RPC-контракты и внешние идентификаторы.
- Не реализовывать собственный C++ балансировщик внутри event service: использовать существующие `mixtura_balance` и `mixtura_balancer_tournament` как внешние сервисы.
