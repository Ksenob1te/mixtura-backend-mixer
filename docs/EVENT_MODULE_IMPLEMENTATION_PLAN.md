# План реализации модуля мероприятий

## Назначение
- Модуль мероприятий реализует организационный цикл события из `WORK.md`: создание мероприятия, прием участников, обработку заявок, формирование выборки, формирование команд, построение сетки матчей, фиксацию результатов и завершение события.
- Модуль не является публичным REST API. Внешний REST находится в Gateway, а этот сервис должен предоставлять внутренние RPC-команды через RabbitMQ/FastStream.
- Модуль владеет только данными мероприятий. Пользователи, пользовательские пространства, интеграции, игровые роли, рейтинги и вычислительное ядро балансировки являются внешними модулями и должны вызываться через RPC/задачи, а не через прямой доступ к их БД.

## Требования Из WORK.md
- Поддержать разные типы мероприятий: турнирная сетка и одиночный матч.
- Поддержать мероприятия внутри пользовательского пространства, чтобы разные сообщества имели собственную базу игроков, дисциплины, роли и рейтинговые шкалы.
- Поддержать регистрацию через заявки и свободное присоединение без предварительного рассмотрения.
- Дать организатору возможность задавать обязательные игровые/социальные интеграции, дополнительные текстовые поля заявки и доступные игровые роли.
- При подаче заявки сохранить ответы на кастомные поля, выбранные интеграции и приоритеты игровых ролей участника.
- Дать организатору возможность принимать и отклонять заявки; принятая заявка должна создавать игрока мероприятия.
- Поддержать выборку игроков для конкретного цикла формирования команд, включая повторные выборки при `allow_multiple_drafts`.
- Поддержать автоматическое формирование команд с учетом рейтингов, ролей, предпочтений, размера команды и ограничений состава.
- Перед формированием команд использовать расчетный рейтинг: `effective_rating` из внешнего рейтингового сервиса, если интеграция включена, или open-rating snapshot с явным источником, если расчет эффективного рейтинга выключен.
- Для формирования команд возвращать несколько вариантов распределения с метриками качества, чтобы организатор мог выбрать один вариант.
- Поддержать капитанский драфт: назначение капитанов и выбор игроков капитанами из выборки. Эта возможность реализуется поздним этапом после базовых одиночных игр и сложных сеток.
- Поддержать турнирные структуры: сетка, стадии, группы, форматы стадий `single_elimination`, `double_elimination`, `round_robin`, `swiss`.
- Поддержать одиночный матч как частный случай сетки: одна стадия, одна группа, один матч.
- Фиксировать участников матча, счет команд, победителя/ничью, продвижение по сетке и итоговые места для турниров; для серии одиночных игр фиксировать match results и итоговый summary/statistics события.
- После завершения мероприятия сформировать данные для модуля рейтингов, но расчет рейтинга выполняется во внешнем рейтинговом сервисе.

## Текущее Состояние
- ORM-модели и репозитории в основном отражают таблицы модуля мероприятий, но миграции не полностью синхронизированы с моделями, например в миграции нет `event_table.status`.
- Текущие `src/core/service/*.py` написаны под старую модель без DTO и неактуальны: они импортируют `src.domain.*`, используют DTO как изменяемые ORM-объекты и вызывают методы, которых нет в DTO.
- Тестовый слой также старый; его приводить в порядок отдельно на этапе 9.
- Рабочей точки входа нет: `start.py` и `entrypoint.sh` ссылаются на отсутствующие модули.
- Вывод: старые сервисы нужно не чинить точечно, а заменить новым слоем use cases под текущую DTO/repository-архитектуру.

## Целевая Архитектура Модуля
- `src/core/models`: предметные DTO и enum-ы предметной области. Для сохраняемых сущностей использовать разделение DTO на `*Create`, `*Read` и, только при наличии изменяемых полей, `*Update`.
- `src/core/commands`: входные DTO команд RPC, например `CreateEventCommand`, `SubmitApplicationCommand`, `GenerateBracketCommand`.
- `src/core/results`: DTO результатов сложных операций, например `TeamFormationVariant`, `BracketView`, `EventSummary`.
- `src/core/interfaces/repo`: протоколы репозиториев, уже частично есть.
- `src/core/interfaces/clients`: протоколы только тех внешних сервисов, к которым Event Service сам ходит через очередь: `RatingClient`, `MixBalancerClient`, `TournamentBalancerClient`.
- `src/core/usecases`: новый слой сценариев вместо текущих stale services.
- `src/infra/postgre/models` и `src/infra/postgre/repo`: ORM и репозитории PostgreSQL.
- `src/infra/rabbit`: FastStream app, RPC handlers и publishers задач.
- `src/infra/clients`: RabbitMQ RPC-клиенты rating service и двух balancer services. Клиентов Server Service в Event Service не должно быть.
- `src/config/event_flow.ini`: источник допустимых переходов глобального lifecycle статуса события. Линейный автомат актуален для событий, проходящих в один цикл, а для повторяемых одиночных игр нужен отдельный active/ongoing режим; операционные состояния регистрации, выборок, формирования команд и матчей должны жить в отдельных сущностях.

## Правило Работы С Моделью
- Реализация должна идти от уже существующих моделей, DTO, репозиториев и таблиц Event Service. Не проектировать параллельную новую схему, если текущие сущности можно расширить небольшим понятным изменением.
- Изменения модели допускаются только если существующая модель не выражает обязательный сценарий этапа. Предпочитать минимальные расширения существующих сущностей новым сущностям.
- Каждое изменение ORM-модели, DTO, enum-а или repository contract обязательно документировать в `EVENT_MODEL_CHANGELOG.md`: указать этап, затронутые файлы/сущности, причину изменения и почему нельзя было обойтись текущей моделью.
- `EVENT_MODEL_CHANGELOG.md` не является migration notes и не требует синхронизации Alembic. Он нужен, чтобы следующий агент видел осознанные отклонения от исходной модели.

## Интеграция С Внешними Сервисами
- Подробный контракт зафиксирован в `EXTERNAL_BALANCER_RANKER_INTEGRATION.md`; при расхождении использовать код внешних сервисов как источник истины.
- Контракт с Gateway/Server Service зафиксирован в `SERVER_GATEWAY_EVENT_INTEGRATION.md`; Event Service не обращается в Server Service напрямую. Gateway получает нужные данные из Server Service и передает в Event Service `access_data` как `AccessDataRequest`, заменяющий JWT для внутренних RPC-команд.
- Рейтинг-сервис `mixtura_ranker` предоставляет RPC `rating.effective.calculate` и `rating.match.process`, но обе интеграции должны быть конфигурируемыми.
- Перед балансировкой модуль мероприятий должен собрать открытые оценки игроков по ролям. Если `rating.effective.calculate` включен, нужно получить `effective_rating` для каждой пары `member_id + role_id`; если выключен, балансировщик получает open-rating snapshot как расчетный рейтинг с явной пометкой источника.
- В `mixtura_balance` и `mixtura_balancer_tournament` поле `PlayerRole.rating` должно заполняться расчетным рейтингом из rating snapshot: `effective_rating` из ranker при включенном расчете или open-rating snapshot при выключенном расчете.
- `mixtura_balance` слушает `mix_balance_service.balance` и подходит для одиночного матча/двух команд.
- `mixtura_balancer_tournament` в текущем `app/main.py` слушает `tournament_balance_service.balance` и публикует прогресс в `mix_balance_service.balance.progress`; README/examples в том репозитории местами используют старое имя `mix_balance_service.balance`, это нужно выровнять до интеграции.
- После фиксации результата матча модуль мероприятий должен сформировать payload для `rating.match.process`; отправка включается отдельной настройкой и может быть отключена для окружений без rating updates.
- Server Service уже содержит restrictions `server_ban`, `mix_ban`, `tournament_ban`; Event Service должен применять их из `access_data.restriction_mask` при создании/участии в мероприятиях.
- Server Service должен получить event-specific permissions из списка ниже. Это внешние административные права на уровне пользовательского пространства, а не замена локальной роли организатора. Event Service принимает уже рассчитанный `access_data.permission_mask` от Gateway и не вычисляет permissions самостоятельно.

## Permissions Для Server Service
- `event_create`: создавать мероприятия в пользовательском пространстве, если создание не открыто всем участникам пространства.
- `event_admin_view`: просматривать непубличные мероприятия и административные данные мероприятий без локальной роли организатора.
- `event_admin_update`: административно изменять настройки и статус любого мероприятия пространства без локальной роли организатора.
- `event_admin_manage_organizers`: произвольно добавлять, удалять и заменять организаторов любого мероприятия пространства.
- `event_admin_manage_players`: административно управлять заявками, участниками и составами любого мероприятия пространства.
- `event_admin_manage_bracket`: административно менять сетку, стадии, группы, посев и результаты матчей любого мероприятия пространства.
- `event_admin_cancel`: административно отменять любое мероприятие пространства.
- `event_admin_complete`: административно завершать стадии и мероприятия при необходимости ручного вмешательства.

Локальный organizer в Event Service имеет полную власть над своим мероприятием независимо от server permissions. Server permissions нужны для внешних административных override-сценариев на уровне пользовательского пространства: создать мероприятие, зайти в администрирование чужого мероприятия, восстановить или заменить организаторов, исправить состояние мероприятия. Обычные действия организатора вроде настроек регистрации, обработки заявок, формирования команд, сетки и результатов не должны требовать отдельных server permissions, если пользователь уже является organizer конкретного event.

## Исправление Модели Данных
- Добавить к `Event` поле `server_id`, иначе модуль не выполняет требование изоляции мероприятий по пользовательским пространствам.
- Явно оформить enum-ы: `EventMatchType`, `TeamFormation`, `EventStatus`, `ApplicationStatus`, `DraftStatus`, `StageFormat`, `MatchSlotSourceType`, `BracketPosition`.
- Для сохраняемых сущностей разделять DTO по сценарию: `*Create` для создания без БД-сгенерированных полей, `*Read` для сохраненного состояния с `id` и серверными полями, `*Update` для частичных изменений.
- `*Update` DTO не обязателен для каждой сущности. Если сущность создается, читается и удаляется, но не имеет осмысленных изменяемых полей, `*Update` не создавать. Пример: organizer может иметь `OrganizerCreate` и `OrganizerRead`, но не иметь `OrganizerUpdate`.
- Отдельные command DTO нужны на RPC-границе, когда входной запрос отличается от DTO сущности или включает внешние данные: например `CreateEventCommand`, `SubmitApplicationCommand`, `RecordMatchResultCommand`.
- Не мутировать frozen DTO. Обновления выполнять через соответствующий `*Update` DTO или репозиторные patch/update-методы.
- Использовать современную нотацию типов: `X | None` вместо `Optional[X]`, `A | B` вместо `Union[A, B]`, встроенные generic-типы `list[T]`, `dict[K, V]`, `set[T]`, `tuple[...]`, `type[T]` вместо `typing.List`/`Dict`/`Set`/`Tuple`/`Type`.
- Пересмотреть смысл `EventStatus`: он должен описывать глобальный lifecycle мероприятия, но не обязан быть одинаковым для всех режимов. Для single-pass событий допустим линейный flow `CREATED -> REGISTRATION -> FORMATION -> IN_PROGRESS -> COMPLETED`; для повторяемых одиночных игр нужен active/ongoing режим, в котором регистрация, выборки, team formation jobs, игроки и матчи имеют собственные статусы и не блокируют друг друга глобальным `EventStatus`.
- Не использовать `FORMATION`/`IN_PROGRESS` как lock всего event в режиме повторяемых одиночных игр: во время активного события могут параллельно приходить новые игроки, уходить старые игроки, формироваться новые выборки и идти несколько матчей.
- Перенести допустимые глобальные переходы в use cases или доменные функции. Открытие/закрытие регистрации для ongoing одиночных игр должно быть отдельной настройкой или окном, а не обязательным глобальным статусом event.
- Уточнить `Draft`: в терминах работы это выборка игроков, а не только драфт капитанов. Название в коде можно сохранить, но в use cases использовать термин `selection`/`draft` как выборку.
- Не добавлять PostgreSQL-модели для вариантов балансировки. `TeamFormationVariant` должен быть result/cache DTO, а варианты `team_formation_variant`/`team_formation_variant_player` хранятся временно в Redis до выбора organizer-ом.
- Добавить статусы/поля для игрока мероприятия, если нужно различать активных, ожидающих, выбранных в текущую выборку и уже играющих.
- Зафиксировать требуемые изменения ORM-моделей и DTO. Alembic не синхронизировать в рамках этой задачи; миграции остаются вне этого ТЗ.
- Все изменения модели фиксировать в `EVENT_MODEL_CHANGELOG.md`.

## Этап 1. Стабилизация Базы
- Заменить старые импорты `src.domain.*` на `src.core.*` или удалить старый сервисный слой перед переписыванием.
- Привести `src/core/models` к контракту `*Create`/`*Read`/опциональный `*Update`: create-flow не должен требовать заранее заданные `id`, timestamps и другие ORM/БД-сгенерированные поля; read-flow должен возвращать `*Read`.
- Проверить контракт репозиториев под раздельные DTO: `create` принимает `*Create`, `get`/`list` возвращают `*Read`, `update`/`patch` принимают `*Update` только для сущностей, которые реально обновляются.
- Синхронизировать `src/infra/postgre/models` и DTO; Alembic не трогать, миграции остаются вне этого ТЗ.
- Если этап меняет ORM/DTO/enums/repository contract, обязательно обновить `EVENT_MODEL_CHANGELOG.md`.
- Не заниматься тестовым слоем на этом этапе; тестирование и фикстуры вынесены в этап 10.
- Критерий готовности этапа: `uv run mypy src` проходит или оставшиеся ошибки явно относятся к еще не реализованным следующим этапам.

## Этап 4.5. Фикс Permissions И Restrictions
- Исправить interpretation of `permission_mask`/`restriction_mask` после этапов 1-4 и до этапа 5.
- Использовать canonical enum order из Server Service `src/infra/postgre/static/permissions.py` и `restrictions.py`.

- Критерий готовности этапа: access helpers Event Service интерпретируют masks так же, как Server Service, без runtime-зависимости от Server Service.

## Этап 5. Выборка И Формирование Команд
- Реализовать `CreateDraftUseCase` как формирование выборки: выбрать игроков мероприятия вручную или автоматически по лимиту, статусам, pinned-флагу и ограничениям. Занятость игрока определять через наличие игрока в активной выборке, которая уже связана с незавершенным матчем; таких игроков исключать из новых выборок, если параллельное участие запрещено.
- Реализовать подготовку рейтингового снапшота: собрать open-rating по ролям; если `rating.effective.calculate` включен, сопоставить ответ обратно с игроками и ролями; если выключен, использовать open-rating как расчетный рейтинг и сохранить источник в snapshot.
- Реализовать постановку задачи формирования команд во внешний балансировщик: подготовить игроков, роли, расчетные рейтинги, предпочтения и ограничения. Подроли сейчас не поддерживать, потому что Server Service пока не предоставляет их в role set.
- Выбирать `mixtura_balance` для двухкомандного одиночного матча и `mixtura_balancer_tournament` для турнирного формирования нескольких команд.
- Сохранять несколько вариантов распределения с метриками во временном Redis-хранилище: разница силы команд, ролевое соответствие, разброс рейтингов, нарушения ограничений.
- Сохранять не только итоговые команды, но и rating snapshot: open-rating, effective-rating и источник/время расчета для диагностики решений.
- Реализовать выбор варианта организатором и материализацию в `Team`/`TeamPlayer`.
- Критерий готовности этапа: из утвержденных игроков можно получить несколько вариантов команд и зафиксировать выбранный вариант.

## Этап 6. Одиночные Игры: Матчи И Слоты
- Приоритет реализации: сначала полностью поддержать одиночные игры, и только потом сложные турнирные сетки.
- Реализовать одиночные игры как повторяемое создание матчей внутри активного event: один event может иметь несколько последовательных или параллельных матчей.
- Для ongoing одиночных игр один раз создать и дальше переиспользовать single-game контейнер `Bracket -> Stage -> StageGroup`; каждый новый цикл создает новый `Match -> MatchSlot` внутри этого контейнера.
- Назначить две или нужное количество команд в fixed slots конкретного матча.
- Создать `MatchScore` stubs, если модель предполагает отдельные score-строки до фиксации результата.
- Не реализовывать на этом этапе `single_elimination`, `double_elimination`, `round_robin`, `swiss`, BYE, standings и маршрутизацию победителей.
- Критерий готовности этапа: внутри активного события можно создавать один или несколько одиночных матчей со слотами и score stubs, готовых к фиксации результата на этапе 7.

## Этап 7. Одиночные Игры: Результаты И Завершение
- Реализовать фиксацию счета одиночного матча без автоматического завершения всего event.
- Реализовать определение победителя, ничьи и технического поражения для одиночных матчей.
- Реализовать формирование результата завершенного матча для `rating.match.process`; отправлять payload только если интеграция rating updates включена. Передавать команды, `team_ranks`, роли игроков и open-rating snapshot на момент матча.
- После завершения матча освобождать/обновлять статусы участвовавших игроков, чтобы они могли участвовать в новых выборках и матчах.
- Реализовать явное завершение одиночного события отдельной командой: проверить, что нет активных матчей и незавершенных обязательных операций, зафиксировать итоговые данные и перевести event в `COMPLETED`.
- Не реализовывать на этом этапе продвижение по турнирной сетке, standings и `advance_count`.
- Критерий готовности этапа: одиночные матчи можно завершать независимо, event продолжает принимать новые циклы до явного завершения organizer-ом.

## Этап 8. Сложные Турнирные Сетки
- Реализовать создание стадий и групп с настройками формата: `single_elimination`, `double_elimination`, `round_robin`, `swiss`.
- Реализовать seed участников в `BracketPlacement` с учетом рейтингов команд.
- Реализовать генераторы матчей по форматам:
- `single_elimination`: дерево победителей, BYE для неполной степени двойки.
- `double_elimination`: верхняя и нижняя сетки, маршрут победителей/проигравших.
- `round_robin`: все пары внутри группы, `meetings_per_pair`.
- `swiss`: генерация следующего раунда по текущим очкам без повторных пар.
- Реализовать продвижение победителей/проигравших по слотам следующих матчей.
- Реализовать standings для round robin и swiss.
- Реализовать завершение стадии и перевод участников в следующую стадию через `advance_count`.
- Критерий готовности этапа: турнирные форматы создают валидные матчи и поддерживают продвижение/standings до итоговой таблицы.

## Этап 9. Captain Draft
- Реализовать captain draft после базовой поддержки одиночных игр и сложных сеток.
- Назначать капитанов из выборки через `DraftedPlayer.is_captain`, без отдельной сущности `Captain`.
- Поддержать очередность выбора, доступный пул игроков, пропуск/автопик при необходимости и завершение captain draft flow на уровне `Draft`/selection.
- Формировать `Team` постепенно по мере выбора игроков капитанами; после завершения captain draft материализовать финальные составы в `TeamPlayer`, если это еще не сделано.
- Captain draft не должен блокировать автоматическое формирование команд из этапа 5 и не входит в single-game MVP.
- Критерий готовности этапа: капитаны могут выбрать игроков из выборки, после чего создаются команды, пригодные для одиночных матчей или турнирных сеток.

## Этап 10. Тестирование

## Этап 11. MVP-Срез
- MVP-1: создание события, настройка заявок, публикация, подача и обработка заявок.
- MVP-2: выборка игроков, расчет эффективных рейтингов через ranker и автоматическое формирование команд через существующий внешний балансировщик.
- MVP-3: одиночные игры как повторяемое создание match-структур внутри активного event.
- MVP-4: фиксация результатов одиночных матчей, обновление статусов игроков и явное завершение события.
- MVP-5: RabbitMQ RPC handlers для Gateway и события для рейтингового сервиса.
- Расширение после single-game MVP: сложные турнирные сетки из этапа 8, captain draft из этапа 9, выравнивание очередей tournament balancer, расширенные метрики и повторные draft-циклы.

## Не Делать На Первом Этапе
- Не восстанавливать старые `src/core/service/*.py` точечными правками: они концептуально расходятся с текущей DTO-моделью.
- Не добавлять unsuffixed ORM aliases в `src.infra.postgre.models` ради старых импортов.
- Не реализовывать публичный REST внутри этого сервиса; REST принадлежит Gateway.
- Не обращаться напрямую к БД auth/space/rating сервисов; только RPC-контракты и внешние идентификаторы.
- Не реализовывать собственный C++ балансировщик внутри event service: использовать существующие `mixtura_balance` и `mixtura_balancer_tournament` как внешние сервисы.
