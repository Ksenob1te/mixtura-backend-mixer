# ТЗ Для Агента: Этап 3. Управление Мероприятиями

## Цель
Реализовать базовые use cases управления мероприятием: создание, чтение, настройка, публикация/открытие регистрации, отмена и управление organizers. После этапа событие можно создать, настроить, опубликовать, отменить и получить через RPC.

## Общий Контекст
- Event Service владеет событиями и связанными aggregate root, но не владеет пользователями, server spaces, ролями и рейтингами.
- Все внешние данные от Server Service приходят через Gateway в payload RPC-команд.
- Внутренний auth context представлен `AccessDataRequest`.
- `Event.server_id` обязателен для изоляции мероприятий по пользовательским пространствам.
- Локальный organizer имеет полную власть над своим мероприятием независимо от server permissions.
- Server permissions нужны только для `event_create` и server-admin override-действий.
- Restrictions из `access_data.restriction_mask` применяются при создании, участии и organizer-действиях.

## Статусная Модель
- `EventStatus` описывает глобальный lifecycle мероприятия, но его смысл зависит от режима события.
- Для single-pass событий актуален линейный поток: `CREATED -> REGISTRATION -> FORMATION -> IN_PROGRESS -> COMPLETED`, плюс `CANCELLED` из разрешенных состояний по `src/config/event_flow.ini`.
- Для повторяемых одиночных игр нужен active/ongoing режим: регистрация не должна быть обязательным глобальным статусом event, а открытие/закрытие регистрации задается настройками, окнами времени или отдельным registration state.
- Формирование выборок, team formation jobs, игроки и матчи имеют собственные статусы и могут идти параллельно внутри ongoing одиночного event.
- Не использовать `FORMATION`/`IN_PROGRESS` как lock всего мероприятия в режиме повторяемых одиночных игр: новые игроки могут приходить, старые уходить, а несколько матчей могут идти параллельно.
- Статусные переходы не должны быть методами mutable DTO.
- Глобальные переходы реализовать в use cases или чистых доменных функциях. Для single-pass flow нужны переходы регистрации/formation/in-progress, для ongoing одиночных игр нужны activate/complete/cancel без блокировки внутренних операций.

## Основные Use Cases
- `CreateEventUseCase`: проверяет `access_data`, server context, restrictions, permission на создание при необходимости, создает `Event`, создает первого `Organizer`, сохраняет выбранные роли и настройки заявок.
- `GetEventUseCase`: возвращает публичную карточку или полную карточку в зависимости от публичности, членства, organizer/admin прав.
- `ListEventsUseCase`: возвращает публичные события пространства и приватные события при наличии контекста.
- `UpdateEventUseCase`: меняет конфигурацию события до начала приема заявок или в разрешенных состояниях.
- `OpenRegistrationUseCase`/`UpdateRegistrationSettingsUseCase`: для single-pass event может переводить событие в `REGISTRATION`, а для ongoing одиночных игр открывает/закрывает регистрацию через settings/window без смены глобального статуса на `REGISTRATION`.
- `CancelEventUseCase`: отменяет событие с проверкой organizer или `event_admin_cancel`.
- `ManageOrganizersUseCase`: добавляет, удаляет и меняет локальных organizers события.

## Конфигурация События
- Публичность и видимость карточки.
- Тип мероприятия: турнирная сетка или одиночный матч.
- Тип регистрации: через заявки или свободное присоединение.
- Размер команды.
- Способ формирования команд: автоматическое формирование или ручной режим. Captain draft реализуется отдельным поздним этапом и не должен блокировать MVP.
- Рейтинговая шкала пространства.
- Доступные игровые роли пространства.
- Обязательные интеграции.
- Кастомные поля заявки.
- Ограничения по времени приема заявок.

## Access Rules
- Создатель события становится локальным organizer.
- Organizer может управлять своим мероприятием без server permissions.
- `event_admin_manage_organizers` позволяет восстановить доступ, заменить organizers или назначить новых organizers без локальной роли.
- `event_admin_update` позволяет административно изменить настройки/статус чужого мероприятия.
- `server_ban` запрещает создание и organizer-действия.
- `mix_ban` и `tournament_ban` не должны запрещать organizer-действия, если бизнес-правило допускает неучаствующего organizer; участие запрещать на этапе заявок/игроков.

## RPC
- `event.create`: создать событие и первого organizer.
- `event.get`: получить карточку события; возвращать public/full view по access rules.
- `event.list_public`: получить публичные события пространства.
- `event.list_private`: получить события пространства с учетом membership/access_data.
- `event.update`: изменить базовую конфигурацию события.
- `event.activate`: опубликовать/активировать event.
- `event.registration.open`: открыть регистрацию через status transition для single-pass event или settings/window для ongoing single-game event.
- `event.registration.close`: закрыть регистрацию через settings/window или допустимый transition.
- `event.cancel`: отменить событие.
- `event.organizer.list`: получить organizers события.
- `event.organizer.add`: добавить organizer.
- `event.organizer.remove`: удалить organizer.

## Критерии Приемки
- Событие можно создать через RPC/use case.
- Создатель становится organizer.
- Событие можно прочитать как публичную карточку и как полную organizer-карточку.
- Событие можно настроить до приема заявок.
- Для single-pass event событие можно перевести в регистрацию; для ongoing одиночных игр регистрацию можно открыть/закрыть через настройки без глобального lock. Событие можно отменить.
- Organizer-действия работают без server permissions.
- Server-admin override permissions работают только для административных сценариев.
