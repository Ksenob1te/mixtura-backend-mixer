# ТЗ Для Агента: Этап 1. Стабилизация Базы

## Цель
Стабилизировать базовый слой Event Service так, чтобы текущая DTO/repository-архитектура стала рабочей основой для дальнейших use cases. Результат этапа должен убрать stale-зависимости от старой доменной модели и привести DTO, ORM-модели и репозитории к единому контракту.

## Общий Контекст
- Event Service реализует организационный цикл мероприятия: создание события, прием участников, заявки, выборки, команды, сетки, матчи, результаты и завершение.
- Event Service не является публичным REST API. REST находится в Gateway, а Event Service предоставляет внутренние RPC-команды через RabbitMQ/FastStream.
- Event Service владеет только данными мероприятий. Пользователи, пользовательские пространства, интеграции, игровые роли, рейтинги и балансировщики являются внешними модулями.
- Event Service не обращается в Server Service напрямую. Gateway получает данные из Server Service и передает в Event Service `AccessDataRequest` и необходимые payload-данные.
- Alembic не синхронизировать в рамках этого этапа; миграции остаются вне этого ТЗ.

## Текущее Состояние
- ORM-модели и репозитории в основном отражают таблицы модуля мероприятий, но не все DTO/ORM/репозитории синхронизированы.
- Текущие `src/core/service/*.py` устарели: импортируют `src.domain.*`, используют DTO как изменяемые ORM-объекты и вызывают методы, которых нет в DTO.
- Тестовый слой устарел, но его не нужно исправлять в этом этапе. Тестирование и фикстуры вынесены в этап 10.
- `start.py` и `entrypoint.sh` ссылаются на отсутствующие модули.
- Старые сервисы не нужно чинить точечно. Их нужно удалить или заменить новым слоем use cases на следующих этапах.

## Архитектурные Правила
- Реализация должна опираться на уже существующие модели, DTO, репозитории и таблицы Event Service. Не проектировать параллельную новую схему, если текущие сущности можно расширить небольшим понятным изменением.
- Изменения модели допускаются только если существующая модель не выражает обязательный сценарий этапа. Предпочитать минимальные расширения существующих сущностей новым сущностям.
- Каждое изменение ORM-модели, DTO, enum-а или repository contract обязательно документировать в `docs/EVENT_MODEL_CHANGELOG.md`: указать этап, затронутые файлы/сущности, причину изменения и почему нельзя было обойтись текущей моделью.
- `docs/EVENT_MODEL_CHANGELOG.md` не является migration notes и не требует синхронизации Alembic.
- DTO классы живут в `src/core/models/<entity>.py` и разделяются по сценарию: `*Create`, `*Read` и опциональный `*Update`, например `EventCreate`, `EventRead`, `EventUpdate`.
- ORM классы живут в `src/infra/postgre/models/<entity>.py` и имеют `*Model` имена, например `EventModel`, `ApplicationModel`.
- Репозитории живут в `src/infra/postgre/repo/<entity>.py`, наследуют общий base repository, задают ORM model и read/create/update DTO-модели по единому контракту.
- Repo protocols живут в `src/core/interfaces/repo/<entity>.py`.
- Не добавлять unsuffixed ORM aliases в `src.infra.postgre.models` ради старых импортов.
- `src/core/models/__init__.py` пустой. Импортировать DTO/enums из конкретных модулей.
- `src/infra/postgre/models/__init__.py` и `src/infra/postgre/repo/__init__.py` остаются export barrels для `*Model` и `*Repository`.
- Таблицы имеют явные имена вида `'<entity>_table'`.
- SQLAlchemy relationships используют `lazy="raise"`, репозиторные `get(...)` методы должны давать `load_*` flags и `selectinload(...)` options.
- Не мутировать frozen DTO. Для изменений использовать соответствующий `*Update` DTO или patch/update-методы репозитория.
- Использовать современную нотацию типов: `X | None` вместо `Optional[X]`, `A | B` вместо `Union[A, B]`, встроенные generic-типы `list[T]`, `dict[K, V]`, `set[T]`, `tuple[...]`, `type[T]` вместо `typing.List`/`Dict`/`Set`/`Tuple`/`Type`.

## Обязательные Изменения Модели
- Добавить или подготовить поле `Event.server_id`, чтобы мероприятия были изолированы по пользовательскому пространству.
- Явно оформить enum-ы: `EventMatchType`, `RegistrationType`, `TeamFormation`, `EventStatus`, `ApplicationStatus`, `DraftStatus`, `StageFormat`, `MatchSlotSourceType`, `BracketPosition`.
- Для сохраняемых сущностей использовать раздельные DTO: `*Create` для создания, `*Read` для сохраненного состояния, `*Update` для частичных изменений.
- `*Create` не должен требовать БД/ORM-сгенерированные поля: `id`, timestamps, computed/server-only поля и default status, если они задаются сервисом или ORM.
- `*Read` должен описывать сохраненное состояние и содержать `id` и серверные поля, которые гарантированы после сохранения.
- `*Update` DTO создавать только для сущностей с осмысленными изменяемыми полями. Если сущность создается, читается и удаляется, но не обновляется, `*Update` не нужен.
- Пример: `OrganizerCreate` и `OrganizerRead` нужны, но `OrganizerUpdate` не нужен, если у organizer нет изменяемых свойств кроме удаления/пересоздания.
- Отдельные command DTO создавать на RPC-границе, когда входной запрос отличается от DTO сущности или включает внешний контекст: `access_data`, role set, rating set, custom/open ratings.
- Уточнить `Draft`: в коде название можно сохранить, но в use cases это выборка игроков `selection`/`draft`, а не только капитанский драфт.
- Добавить модель результата формирования команд, если варианты распределения должны храниться до выбора организатором: `team_formation_job`, `team_formation_variant`, `team_formation_variant_player`.
- Добавить статусы/поля для игрока мероприятия, если нужно различать активных, ожидающих, выбранных в текущую выборку и уже играющих.

## Задачи
- Найти и устранить старые импорты `src.domain.*` в коде, который должен остаться частью нового Event Service.
- Удалить или изолировать stale service layer, если он блокирует import/typecheck и не соответствует новой DTO/repository-архитектуре.
- Привести `src/core/models` к контракту `*Create`/`*Read`/опциональный `*Update`.
- Проверить контракт создания в репозиториях и DTO: create-flow не должен требовать заранее заданный `id`, если `id` генерируется ORM/БД.
- Обновить общий base repository и repo protocols под раздельные DTO: `create` принимает `*Create`, `get`/`list` возвращают `*Read`, `update`/`patch` принимают `*Update` только там, где обновление поддержано.
- Удалить `Optional`, `Union`, `List`, `Dict`, `Set`, `Tuple`, `Type` из нового/затрагиваемого кода в пользу `| None`, `|` и built-in generics.
- Синхронизировать `src/infra/postgre/models` и DTO без изменения Alembic.
- Обновить `docs/EVENT_MODEL_CHANGELOG.md` для каждого изменения ORM/DTO/enum/repository contract.
- Убедиться, что импорты barrel-файлов не создают циклы и не экспортируют stale aliases.

## Не Делать
- Не синхронизировать Alembic и не генерировать миграции.
- Не восстанавливать старые `src/core/service/*.py` точечными правками.
- Не добавлять aliases DTO/ORM ради backward compatibility со stale-кодом.
- Не реализовывать публичный REST внутри Event Service.
- Не обращаться напрямую к БД auth/server/rating сервисов.
- Не реализовывать бизнес-use cases следующих этапов, кроме минимального кода, необходимого для импорта.
- Не исправлять и не писать тесты; тестирование вынесено в этап 10.

## Критерии Приемки
- `uv run mypy src` проходит или список оставшихся ошибок не относится к стабилизируемому слою и явно задокументирован.
- В коде, который импортируется при typecheck/start, нет ссылок на `src.domain.*`.
- DTO и ORM модели согласованы по обязательным полям, enum-ам и split-контракту `*Create`/`*Read`/опциональный `*Update`.
- Все изменения ORM/DTO/enum/repository contract зафиксированы в `docs/EVENT_MODEL_CHANGELOG.md`.
- Alembic файлы не изменены.
