# ТЗ Для Агента: Этап 9. Captain Draft

## Цель
Реализовать captain draft как поздний способ формирования команд после базовой поддержки автоматического баланса, одиночных игр и сложных турнирных сеток. Captain draft не должен блокировать single-game MVP и не должен заменять автоматическое формирование команд из этапа 5.

## Общий Контекст
- Captain draft работает поверх выборки игроков (`Draft`/selection), созданной ранее.
- Captain draft является отдельным flow формирования команд поверх существующей выборки: капитаны выбирают игроков из доступного пула, а команды `Team` формируются постепенно по мере выборов.
- Event Service не обращается в Server Service напрямую. Все данные участников, ролей и access context приходят через Gateway.
- Organizer имеет полную власть над своим мероприятием.
- Server-admin override может использоваться только для административного вмешательства.
- Выбор капитанами не должен менять глобальный `EventStatus`; состояние captain draft должно жить на уровне `Draft`/selection.

## Основные Сущности
- `Draft`: выборка игроков и состояние captain draft flow для конкретного цикла формирования команд.
- `DraftedPlayer`: участник выборки. Капитан определяется флагом `is_captain` на `DraftedPlayer`, а не отдельной сущностью `Captain`.
- `Team`: команда, создаваемая для капитана в начале или в процессе captain draft.
- `TeamPlayer`: игрок команды с назначенной ролью и rating snapshot.

Не добавлять отдельные модели `CaptainDraftSession`, `CaptainDraftPick` или `Captain`, если существующие `Draft`/`DraftedPlayer`/`Team` позволяют выразить состояние и историю выбора. Если нужна история ходов, сначала проектировать ее как поля/порядок на `DraftedPlayer` или как минимальную связанную сущность только после явной необходимости.

## CaptainDraftUseCase
- Проверить доступ: organizer или server-admin override.
- Проверить, что event принадлежит `access_data.server_id`.
- Проверить, что selection существует и принадлежит event.
- Проверить, что selection содержит достаточное количество игроков.
- Назначить капитанов вручную или из заранее выбранных игроков через `DraftedPlayer.is_captain`.
- Создать стартовые `Team` для капитанов или подготовить их создание при первом выборе капитана.
- Зафиксировать порядок выбора.
- Поддержать получение доступного пула игроков.
- Поддержать pick игрока капитаном: выбранный `DraftedPlayer` привязывается к команде капитана, а команда формируется постепенно.
- Поддержать skip/auto-pick, если такая настройка включена.
- Завершить captain draft, когда все required picks сделаны или когда достигнуты настройки состава.
- Материализовать финальные составы в `TeamPlayer`, если по ходу выбора сохранялась только связь `DraftedPlayer -> Team`.
- Для manual/captain flows role assignment и rating snapshot приходят с клиента/Gateway payload; Event Service валидирует и сохраняет их, но не обращается за ними в Server Service.

## Статусы
- `Draft`/selection должен иметь статус captain draft flow, например `CREATED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`, или совместимый статусный набор в существующем `DraftStatus`.
- Статус selection/draft должен позволять понять, используется ли выборка в captain draft, auto balance или уже материализована.
- Глобальный `EventStatus` не должен переходить в `FORMATION`/`IN_PROGRESS` только из-за captain draft.

## Критерии Приемки
- Organizer может запустить captain draft flow для выборки.
- Капитаны могут выбирать игроков из доступного пула.
- Капитан определяется через `DraftedPlayer.is_captain`.
- Игрок не может быть выбран дважды.
- По мере captain draft формируются `Team`, а после завершения доступны финальные составы `TeamPlayer`.
- Созданные команды можно использовать в одиночных матчах или турнирных сетках.
